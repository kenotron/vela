# Spike S-3 — spike-handle-dispatch

Tests Assumptions A5, A6, A9 together against lane 1.4's stock
`amplifier-agent serve` deployment: does a handle-returning host tool
(`dispatch_to_fleet`-shaped) complete a chat-completions turn normally, and
does the resulting ledger record survive into a **subsequent turn in the
same session** after `amplifier-agent`'s transcript reconciliation?

## What's here

- `ledger.py` — minimal standalone in-memory ledger stub, local to this
  spike (per goal file: lane 2.1's real ledger service was not yet merged
  when this spike ran, so this substitutes for it; mirrors the shape of
  lane 1.3's `InMemoryLedgerRepository.kt`, read-only reference, not
  modified).
- `spike.py` — the spike itself. Pure HTTP/CLI (stdlib `urllib` only, no
  external deps available in this environment). Runs against the live
  `vela-agent-serve` systemd unit at `127.0.0.1:9099` (lane 1.4).
- `results.json` — raw output of the most recent run (generated by
  `spike.py`, gitignored is NOT set for this — see note below).

## Running it

```bash
export AMPLIFIER_AGENT_HTTP_API_KEY=$(grep AMPLIFIER_AGENT_HTTP_API_KEY ~/.amplifier/vela-agent-serve/env | cut -d= -f2)
python3 spike.py
```

## Method

1. **Item 1 (p99 < 1s over >=10 calls):** measures the tool's own
   synchronous execution latency directly — 12 calls to
   `ledger.append(...)`, sorted, p99 computed. This is what the design
   doc's §11.2 perf target and `DispatchToFleetTool.maxSyncMillis = 1000L`
   actually constrain (the tool's own work), not the LLM round trip.
2. **Item 2 (turn completes normally):** a live turn against
   `vela-agent-serve` (`stream: true`, matching S-2's finding that
   `tool_calls` only populate reliably in streamed SSE deltas). The model
   calls `dispatch_to_fleet`, the tool result is executed locally
   (ledger-write-before-return, mirroring `DispatchToFleetTool.kt`'s
   ordering), and re-POSTed as a `{role: "tool", ...}` message. A normal
   final assistant message is produced — no hang, no error.
3. **Item 3 (subsequent turn, same session, ledger retrieval):** a second
   user message is appended to the **same `messages` array** (now carrying
   turn 1's assistant `tool_calls` + `tool` result messages — the exact
   "orphaned tool_use block" scenario A6 worries about). The model is asked
   to call a new `query_ledger` tool for the job_id from turn 1. The turn
   completes normally and the ledger lookup succeeds.
4. **Item 4 (A6 documentation):** see finding in `results.json` / below.

## Result

All four items: **PASS**. Full machine-readable evidence in `results.json`
(one full live run, git-tracked as of this commit — see Residuals).

### Item 4 finding (A6)

The ledger record lives in a process-local Python object entirely outside
the chat `messages` transcript POSTed to `amplifier-agent serve`.
`amplifier-agent` is a stateless-per-request HTTP server — each
`/v1/chat/completions` call receives the full `messages` array from the
client and returns a response; it does not itself persist or reconcile any
store on the caller's behalf. Therefore transcript reconciliation —
whatever internal bookkeeping the server does with the `messages` it
receives on turn 2 — has **no code path that could touch this spike's
external ledger**.

**F-6 ("ledger record silently lost") cannot manifest via server-side
transcript reconciliation for an external ledger store.** It could only
manifest from a *client*-side bug (the client itself failing to
append/replay the `tool_use`+`tool_result` pair correctly on the second
POST) — which is exactly what item 3's live test exercises, and it passed:
the second POST (containing the full accumulated transcript from turn 1)
was accepted and processed normally by the live server, and the ledger
query it triggered returned the correct record.

**Practical implication for the real implementation (lane 3.x and beyond):**
as long as the client-side transcript accumulation logic (already proven
correct here, matching `AmplifierToolLoopClient`'s pattern from lane 1.3) is
used consistently turn-over-turn, an out-of-band ledger (SQLite locally, or
a networked ledger service once lane 2.1 lands) is safe from any
transcript-reconciliation-related loss. The durability boundary is the
ledger's own write, not anything to do with the chat transcript.

## Residuals

- **`amplifier-agent`'s internal reconciliation implementation was not
  inspected directly** (out of scope / closed-source-to-this-spike from
  this vantage point — it's lane 1.4's dependency, "stock, unmodified").
  This spike verifies *observable behavior* (the turn completes, the
  ledger is reachable) rather than reading `amplifier-agent`'s source for
  its reconciliation code. That is sufficient to answer the goal file's
  question ("does the resulting ledger record survive...") but a lower-level
  code-level audit of `amplifier-agent`'s transcript reconciliation is out
  of scope here and not needed given the black-box behavioral evidence.
- **Tailscale/LAN reachability not exercised** — this spike only used
  `127.0.0.1`, per the goal file's host capability limits (headless Linux,
  pure HTTP/CLI). Lane 1.4's `ops/README.md` already documents the
  reachability model; this spike is orthogonal to that (it tests turn/ledger
  mechanics, not network path).
- **Single live end-to-end run for items 2-4** rather than repeated runs —
  the goal file's ">=10 calls" quantitative requirement is scoped to item 1
  (tool execution latency) only; items 2-4 are pass/fail behavioral
  questions about a single documented mechanism, and one clean live
  reproduction is sufficient evidence for a conclusive answer. Re-running
  `spike.py` reproduces the same PASS result (deterministic ledger/tool
  logic; only the LLM's exact wording varies between runs).
